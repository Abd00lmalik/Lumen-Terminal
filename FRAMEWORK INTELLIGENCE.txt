FRAMEWORK INTELLIGENCE

PURPOSE

Framework Intelligence manages persistent trader-defined evaluation methodologies.

A framework defines HOW the trader wants a class of questions, theses, assets, or situations evaluated. It is not itself a thesis, judgment, or research result.

The system must preserve the framework exactly enough that applying it later produces an evaluation according to the trader's stated methodology rather than silently substituting the agent's preferred methodology.

Core principle:

FRAMEWORK = HOW THE TRADER WANTS SOMETHING EVALUATED
THESIS = WHAT THE TRADER BELIEVES
JUDGMENT = WHAT CURRENT EVIDENCE SUPPORTS
RESEARCH = HOW EVIDENCE IS INVESTIGATED

The trader owns the framework. The system applies, explains, tests, and preserves it, but must not silently modify it.

--------------------------------------------------
FRAMEWORK DEFINITION
--------------------------------------------------

A framework is a reusable evaluation methodology consisting of explicit factors, conditions, evidence requirements, weights, thresholds, and evaluation rules.

A framework may be simple or complex.

A simple framework may contain only several factors and qualitative rules.

A complex framework may contain:

- multiple factor groups
- weighted factors
- conditional rules
- dependencies
- thresholds
- hard constraints
- soft signals
- evidence requirements
- aggregation logic
- exception rules
- context-specific conditions

The agent must preserve the distinction between:

- factor importance
- factor weight
- evidence strength
- evaluation result

These are not interchangeable.

A factor can be extremely important while having weak evidence.

A factor can have strong evidence while being relatively unimportant to the framework.

The framework must not confuse these concepts.

--------------------------------------------------
FRAMEWORK CREATION
--------------------------------------------------

Frameworks may be created through natural language.

Examples of valid intent:

"Create a framework for evaluating whether a token is worth researching."

"Save this as my macro framework."

"For every L1 I evaluate, check these five things."

"Create a framework using these criteria."

The agent must:

1. identify the intended framework
2. extract explicit factors
3. identify conditions
4. identify required evidence
5. identify weights when explicitly provided
6. identify thresholds when explicitly provided
7. identify evaluation rules
8. identify scope
9. identify assumptions
10. identify applicability conditions
11. identify missing structural information
12. ask for clarification only when the missing information materially changes the framework

The agent must not invent important framework components merely to make the framework appear complete.

If the trader provides factors but no weights:

use equal weighting by default when weighting is necessary.

If the trader explicitly specifies weights:

preserve those weights.

If the trader provides qualitative importance rather than numerical weights:

preserve the importance designation and do not silently convert it into arbitrary numerical weights.

--------------------------------------------------
FRAMEWORK RESOLUTION
--------------------------------------------------

When the trader says:

"Evaluate this according to my framework"

the system must resolve the intended framework using:

1. explicitly named framework
2. currently active applicable framework
3. framework associated with the current research context
4. framework associated with the relevant thesis/context
5. relevant persistent framework memory
6. clarification if multiple materially different frameworks remain plausible

The system must never silently choose a framework when doing so could materially change the evaluation.

If one framework clearly applies, use it immediately.

--------------------------------------------------
FRAMEWORK SCOPE
--------------------------------------------------

Every framework should have an explicit or inferred scope.

Scope may include:

- asset class
- asset
- sector
- protocol category
- market condition
- research question
- timeframe
- trader objective
- thesis type
- evidence domain

A framework must not automatically be applied outside its intended scope.

If the current target falls outside the framework's known scope, the agent should:

1. identify the mismatch
2. determine whether the framework can reasonably generalize
3. explain the applicability issue
4. ask for confirmation when the difference is material

The agent must not silently expand a framework's scope.

--------------------------------------------------
FACTOR MODEL
--------------------------------------------------

Each framework factor represents a distinct consideration.

A factor should contain:

- factor definition
- importance
- condition
- evidence required
- weight when applicable
- threshold when applicable
- evaluation rule
- dependencies
- current evaluation status

Factors should be sufficiently distinct to avoid double-counting the same evidence.

If two factors substantially measure the same thing, the agent should flag possible overlap.

It must not silently remove or merge them.

--------------------------------------------------
FACTOR IMPORTANCE
--------------------------------------------------

Importance describes how consequential a factor is to the framework.

Possible values may include:

- CRITICAL
- HIGH
- MEDIUM
- LOW
- CONTEXTUAL

Importance does not automatically determine numerical weight unless the framework explicitly defines that relationship.

A CRITICAL factor may remain qualitative.

The system must preserve the trader's intended distinction.

--------------------------------------------------
EVIDENCE REQUIREMENTS
--------------------------------------------------

Each factor may specify evidence required to evaluate it.

Evidence requirements can be:

- mandatory
- preferred
- supporting
- contextual

The system must distinguish:

AVAILABLE EVIDENCE

RESEARCHED EVIDENCE

MISSING EVIDENCE

UNAVAILABLE EVIDENCE

INSUFFICIENT EVIDENCE

A factor must not be marked positively merely because required evidence was not found.

Absence of evidence is not automatically evidence against the factor.

--------------------------------------------------
WEIGHTS
--------------------------------------------------

Weights determine how much a factor contributes to an aggregate evaluation when the framework uses weighted aggregation.

Possible weighting models:

- equal weighting
- explicit numerical weighting
- relative weighting
- category weighting
- rule-based weighting
- qualitative weighting

The agent must preserve explicit trader-defined weights.

If no weights are specified and aggregation requires weights:

use equal weighting by default.

The agent must not fabricate numerical weights based on its own judgment.

If weights do not sum to a standard total, preserve the original values and normalize only for calculation where mathematically necessary.

The original trader-defined weights must remain visible and unchanged.

--------------------------------------------------
THRESHOLDS
--------------------------------------------------

Thresholds define conditions under which a factor changes state or contributes differently.

Thresholds may be:

- numerical
- categorical
- qualitative
- conditional
- evidence-based
- timeframe-dependent

The agent must never invent arbitrary thresholds merely to complete an evaluation.

When a threshold is required but unavailable:

1. identify the missing threshold
2. determine whether a defensible evidence-derived threshold exists
3. if not, mark the factor unresolved
4. explain the consequence

Evidence-derived thresholds may be proposed when supported by the research context, but they must not silently become framework rules.

--------------------------------------------------
EVALUATION RULES
--------------------------------------------------

Evaluation rules define how evidence maps to a factor assessment.

Examples include:

- positive evidence supports the factor
- failure of a required condition weakens the factor
- mandatory condition failure prevents a positive overall evaluation
- factor passes only when specified evidence exists
- factor remains unresolved when required evidence is unavailable

Rules may be:

- deterministic
- conditional
- qualitative
- threshold-based
- comparative
- evidence-based

The agent must follow the framework's existing rules exactly unless the trader explicitly modifies them.

--------------------------------------------------
HARD AND SOFT RULES
--------------------------------------------------

Frameworks may contain:

HARD RULES

Conditions that must be satisfied.

SOFT RULES

Factors that influence the evaluation but do not independently determine the result.

The system must preserve this distinction.

A hard-rule failure must not be diluted by strong soft factors unless the framework itself explicitly permits that.

A soft factor must not be treated as a hard constraint merely because the agent considers it important.

--------------------------------------------------
DEPENDENCIES BETWEEN FACTORS
--------------------------------------------------

Factors may depend on other factors.

Examples:

Factor B may only be evaluated if Factor A passes.

Factor C may modify the interpretation of Factor B.

Factor D may become more important under a specific market condition.

Dependencies must be represented explicitly.

When a factor changes materially, dependent factors must be re-evaluated when necessary.

Unrelated factors should remain untouched.

Circular factor dependencies must be detected and prevented from creating uncontrolled evaluation loops.

--------------------------------------------------
MISSING EVIDENCE
--------------------------------------------------

When required evidence is unavailable, the agent must not manufacture a result.

Possible factor states include:

- PASS
- FAIL
- PARTIALLY_SUPPORTED
- UNRESOLVED
- INSUFFICIENT_EVIDENCE
- NOT_APPLICABLE
- CONFLICTED

Missing evidence should reduce certainty or leave the factor unresolved depending on the framework rule.

The system must distinguish:

"The factor is false"

from

"We do not currently have enough evidence to evaluate the factor."

--------------------------------------------------
FACTOR EVALUATION
--------------------------------------------------

For each factor the system should determine:

1. applicable or not
2. required evidence
3. available evidence
4. evidence quality
5. evidence direction
6. condition status
7. rule result
8. factor status
9. confidence in that factor evaluation
10. unresolved issues

Evidence quality must remain separate from factor outcome.

A factor can pass with high confidence.

A factor can pass with moderate confidence.

A factor can appear favorable but remain low-confidence because the evidence is weak.

--------------------------------------------------
EVIDENCE QUALITY WITHIN FRAMEWORKS
--------------------------------------------------

Framework evaluation uses the broader Evidence Intelligence system.

Evidence should be evaluated using:

- reliability
- directness
- recency
- specificity
- corroboration
- source independence
- provenance
- relevance
- context completeness

The framework determines how that evidence should be interpreted.

Evidence Intelligence determines whether the evidence itself is trustworthy and relevant.

The framework must not override source provenance.

--------------------------------------------------
CONFLICTING EVIDENCE
--------------------------------------------------

When evidence conflicts:

1. preserve both sides
2. evaluate evidence quality
3. examine timeframe
4. examine scope
5. examine definitions
6. examine measurement differences
7. examine source independence
8. determine whether the conflict can be resolved
9. update factor confidence accordingly

If the framework explicitly defines a conflict-resolution rule, apply it.

Otherwise, do not arbitrarily choose the evidence that produces the preferred outcome.

A materially unresolved conflict should be visible in the evaluation.

--------------------------------------------------
CONFLICTING FACTORS
--------------------------------------------------

Different factors may produce opposing evaluations.

The system must not automatically cancel them out.

Instead:

- preserve each factor result
- identify relationships
- apply framework aggregation/rules
- identify dominant factors where the framework defines dominance
- identify unresolved tension
- explain which factors drive the final evaluation

If the framework cannot resolve the conflict, the final result may remain conditional or unresolved.

--------------------------------------------------
AGGREGATION
--------------------------------------------------

After individual factors are evaluated, the framework's aggregation method is applied.

Possible aggregation methods:

- weighted score
- equal-weight score
- rule-based decision
- threshold model
- categorical aggregation
- hierarchical evaluation
- conditional decision tree
- qualitative synthesis

The agent must not substitute a different aggregation method because it appears more convenient.

If no aggregation method is specified:

use the simplest defensible method consistent with the framework structure and clearly state the interpretation.

If aggregation materially depends on missing framework logic, request clarification rather than inventing a methodology.

--------------------------------------------------
OVERALL EVALUATION
--------------------------------------------------

A framework evaluation should produce:

1. overall result
2. strongest positive factors
3. strongest negative factors
4. critical failed conditions
5. unresolved factors
6. evidence gaps
7. conflicts
8. factor-level confidence
9. overall confidence
10. assumptions affecting the result
11. conditions that could change the result

The overall result must be traceable to the factor evaluations.

The system must never output an unsupported overall score.

--------------------------------------------------
IMPORTANCE VS EVIDENCE STRENGTH
--------------------------------------------------

The system must explicitly maintain:

FACTOR IMPORTANCE

How much the trader cares about the factor.

EVIDENCE STRENGTH

How strongly current evidence supports the factor's evaluation.

These must never be conflated.

Example:

A critical factor with weak evidence remains critical but uncertain.

A low-importance factor with extremely strong evidence remains low importance.

The framework's weight and evidence strength are also separate.

--------------------------------------------------
FRAMEWORK INTEGRITY CHECK
--------------------------------------------------

Before finalizing an evaluation, the system must perform a framework integrity check.

Check:

- Was every applicable factor evaluated?
- Were mandatory factors evaluated?
- Were required evidence requirements respected?
- Were weights preserved?
- Were thresholds preserved?
- Were evaluation rules preserved?
- Were hard rules respected?
- Were soft rules treated correctly?
- Were factors double-counted?
- Were missing evidence states preserved?
- Were conflicts represented?
- Were assumptions introduced?
- Was the framework silently modified?
- Was evidence strength confused with factor importance?
- Was a conclusion derived using rules not contained in the framework?

If a problem is found, the system must surface it.

The system must not silently repair the framework.

--------------------------------------------------
FRAMEWORK ASSUMPTIONS
--------------------------------------------------

Frameworks may contain assumptions.

The system should identify:

- explicit assumptions
- structural assumptions
- evidence assumptions
- applicability assumptions
- hidden dependencies discovered during evaluation

The agent may flag an assumption that appears problematic.

It must not silently delete or modify the assumption.

If the assumption materially affects the evaluation, show its effect.

--------------------------------------------------
FRAMEWORK CHALLENGE
--------------------------------------------------

The system may challenge a framework when explicitly requested.

Examples:

"Challenge my framework."

"Is this framework actually useful?"

"Find weaknesses in my evaluation framework."

Framework challenge should examine:

- missing factors
- redundant factors
- double-counting
- weak assumptions
- arbitrary thresholds
- inconsistent rules
- poor evidence requirements
- excessive complexity
- contradictory rules
- blind spots
- overfitting
- sensitivity to individual factors
- inability to handle missing evidence
- instability under changing market conditions

A framework challenge must not automatically modify the framework.

It produces recommendations.

Any consequential framework modification requires trader confirmation.

--------------------------------------------------
FRAMEWORK APPLICATION VS FRAMEWORK CHALLENGE
--------------------------------------------------

Ordinary framework evaluation asks:

"Does the target satisfy my framework?"

Framework challenge asks:

"Is the framework itself sound?"

These are separate operations.

A normal framework evaluation may flag an issue with the framework when necessary, but must not automatically turn the evaluation into a framework redesign.

A CHALLENGE action can explicitly target the framework itself.

--------------------------------------------------
FRAMEWORK MODIFICATION
--------------------------------------------------

Natural language modifications are supported.

Examples:

"Add liquidity as a factor."

"Make regulatory risk more important."

"Remove this factor."

"Change the threshold."

"Use equal weighting."

"Make this a hard requirement."

The agent must determine:

- target framework
- intended modification
- affected factors/rules
- materiality
- downstream effects

Minor changes may update the current version.

Material changes create a new framework version.

Previous versions remain preserved.

The agent must never silently alter a persistent framework.

--------------------------------------------------
MATERIAL FRAMEWORK CHANGES
--------------------------------------------------

Examples of potentially material changes:

- adding/removing a factor
- changing factor weight materially
- changing a hard rule
- changing an evaluation rule
- changing a threshold that can change outcomes
- changing aggregation logic
- changing evidence requirements
- changing framework scope
- changing critical assumptions

Material changes create a new version.

The prior version remains available.

Historical evaluations retain the framework version used at the time.

--------------------------------------------------
FRAMEWORK VERSIONING
--------------------------------------------------

Each material framework version must preserve:

- framework definition
- factors
- weights
- thresholds
- rules
- assumptions
- scope
- evidence requirements
- evaluation model
- provenance
- creation/update timestamps

Historical evaluations must reference the exact framework version used.

A new framework version must not rewrite historical evaluations.

Minor internal updates may remain within the current version when they do not materially alter evaluation behavior.

--------------------------------------------------
FRAMEWORK STATUS
--------------------------------------------------

Framework lifecycle:

DRAFT
→ ACTIVE
→ COMPLETED
→ ARCHIVED

A framework may remain ACTIVE indefinitely.

COMPLETED means the framework creation/modification objective has been completed, not that all future evaluations are complete.

ARCHIVED frameworks remain available historically.

Archived frameworks may be restored only after applicability and validity are rechecked.

A framework may also be marked STALE or INVALID where appropriate.

STALE means the framework may no longer reflect the trader's current methodology or context.

INVALID means the framework should no longer be relied upon without explicit repair/revalidation.

Stale or invalid frameworks remain preserved historically.

--------------------------------------------------
MULTIPLE FRAMEWORKS
--------------------------------------------------

The trader may maintain multiple frameworks.

Examples:

- token evaluation framework
- macro framework
- DeFi risk framework
- trade thesis framework
- protocol research framework

Frameworks may coexist.

The system must not assume one universal framework.

When multiple frameworks apply, the agent should determine whether:

- one is clearly primary
- several should be evaluated independently
- they should be compared
- a combined evaluation is explicitly requested

The system must not silently combine independent frameworks.

--------------------------------------------------
FRAMEWORK COMBINATION
--------------------------------------------------

Frameworks may be combined only when requested or when the framework explicitly defines composition.

Possible composition:

- sequential evaluation
- independent evaluation
- hierarchical evaluation
- intersection of hard requirements
- comparative evaluation

If combination changes the methodology materially, require confirmation before creating a persistent combined framework.

--------------------------------------------------
FRAMEWORK CONTEXT
--------------------------------------------------

Framework evaluation may use:

- current research
- current evidence
- active thesis
- current judgment
- historical research
- previous framework evaluations
- trader preferences

Current validated evidence takes precedence over historical information.

Historical framework evaluations provide context but must not be treated as current evidence.

The framework itself remains authoritative for methodology unless the trader changes it.

--------------------------------------------------
FRAMEWORK AND THESIS
--------------------------------------------------

A framework may evaluate a thesis.

A thesis may also contain references to frameworks used to assess it.

The distinction remains:

FRAMEWORK:
"How should this be evaluated?"

THESIS:
"What do I believe?"

A framework evaluation may show that a thesis fails several framework factors.

The system must not automatically rewrite the thesis.

It may recommend:

- further research
- challenge
- thesis revision
- additional monitoring

The trader decides.

--------------------------------------------------
FRAMEWORK AND JUDGMENT
--------------------------------------------------

A framework may evaluate current research or judgment.

The judgment remains the system's best-supported assessment.

The framework determines how that assessment and its supporting evidence should be evaluated according to the trader's methodology.

A framework must not force the judgment to become favorable or unfavorable.

The framework evaluates.

The evidence determines what can be supported.

--------------------------------------------------
FRAMEWORK AND RESEARCH
--------------------------------------------------

Framework evaluation may trigger research when evidence required by the framework is missing.

The system should identify information requirements from the framework and pass them to RESEARCH.

Example:

Framework requires:

"Evaluate regulatory risk using current jurisdiction-specific evidence."

If current evidence is insufficient, the framework evaluation should trigger targeted research rather than guessing.

Research fills evidence requirements.

Framework rules determine how the resulting evidence is evaluated.

--------------------------------------------------
FRAMEWORK AND ANALYZE
--------------------------------------------------

ANALYZE may be used to interpret evidence gathered for framework factors.

The framework remains the methodology.

ANALYZE remains the analytical operation.

The system should not confuse an analytical finding with a framework factor result.

--------------------------------------------------
FRAMEWORK AND CHALLENGE
--------------------------------------------------

CHALLENGE may:

- challenge a thesis using the framework
- challenge a specific framework factor
- challenge the framework itself

When the framework itself is challenged, the framework remains unchanged until the trader approves modifications.

--------------------------------------------------
FRAMEWORK AND MONITOR
--------------------------------------------------

A framework evaluation may identify conditions worth monitoring.

The system may recommend monitoring when:

- a critical factor is unstable
- a required condition may change
- evidence is likely to change materially
- a threshold may soon be crossed
- a key assumption is under pressure

Monitoring activation requires explicit confirmation when it creates persistent monitoring behavior.

--------------------------------------------------
FRAMEWORK AND MEMORY
--------------------------------------------------

Frameworks are persistent knowledge objects.

Memory should preserve:

- framework versions
- factors
- rules
- weights
- thresholds
- evidence requirements
- historical evaluations
- framework evolution

Historical framework versions must remain distinguishable from the current active framework.

The current framework takes precedence.

Historical versions may be retrieved for comparison or context.

--------------------------------------------------
FRAMEWORK AND SAVE
--------------------------------------------------

SAVE may intentionally preserve:

- a newly created framework
- a framework version
- a framework evaluation
- a framework snapshot
- a framework-related reusable artifact

Normal framework state is automatically persisted.

Explicit SAVE creates intentional reusable persistence.

Material framework changes should be versioned.

Consequential persistent framework changes require confirmation.

--------------------------------------------------
FRAMEWORK EVALUATION OUTPUT
--------------------------------------------------

Default output should be concise and decision-useful.

Preferred structure:

OVERALL EVALUATION

Why

Strongest supporting factors

Strongest opposing factors

Critical conditions

Unresolved factors

Evidence gaps

Conflicts

Confidence

What could change the evaluation

Deeper factor-by-factor evidence and reasoning should remain available through progressive disclosure.

The system should not force the trader to read every factor unless requested.

--------------------------------------------------
PROGRESSIVE DISCLOSURE
--------------------------------------------------

Default:

overall framework result.

On request:

factor-level evaluation.

Further request:

evidence supporting each factor.

Further request:

rules, weights, thresholds, assumptions, dependencies, and calculation.

The complete evaluation trail must remain traceable.

The agent should expose complexity when useful rather than displaying the entire framework graph by default.

--------------------------------------------------
FRAMEWORK CONFIDENCE
--------------------------------------------------

Framework confidence describes confidence in the resulting evaluation.

It is distinct from:

- confidence in individual evidence
- confidence in individual factor evaluations
- thesis confidence
- judgment confidence

Overall framework confidence should consider:

- evidence quality
- evidence completeness
- factor certainty
- unresolved factors
- rule consistency
- applicability
- conflicts
- framework integrity

Do not calculate a numerical probability unless the framework explicitly defines one.

Default confidence levels:

HIGH
MODERATE
LOW

--------------------------------------------------
FRAMEWORK UNCERTAINTY
--------------------------------------------------

Uncertainty should identify why the evaluation may change.

Sources include:

- missing evidence
- conflicting evidence
- ambiguous factor conditions
- uncertain applicability
- unstable market conditions
- unresolved assumptions
- threshold proximity
- incomplete research
- framework limitations

Uncertainty does not automatically mean the framework is weak.

It may simply reflect incomplete current information.

--------------------------------------------------
FRAMEWORK SENSITIVITY
--------------------------------------------------

Where useful, the agent may identify which factors materially drive the overall evaluation.

This includes:

- dominant positive factors
- dominant negative factors
- critical hard-rule failures
- factors whose change could reverse the conclusion
- factors with unusually high uncertainty

Sensitivity analysis should not silently alter weights.

It explains how dependent the result is on particular factors.

--------------------------------------------------
FRAMEWORK ROBUSTNESS
--------------------------------------------------

When useful, the agent may test whether the evaluation remains stable under reasonable changes to uncertain inputs.

Examples:

- uncertain evidence interpretation
- borderline threshold
- conflicting source
- moderate factor change

This is analytical stress testing, not framework modification.

If robustness materially affects the conclusion, show it.

--------------------------------------------------
FRAMEWORK FAILURE HANDLING
--------------------------------------------------

If the framework cannot be applied:

identify the reason.

Possible reasons:

- missing required factor
- invalid framework
- ambiguous rule
- missing threshold
- missing evidence
- incompatible target
- contradictory framework rules
- unresolved dependency
- insufficient data

The system must not fabricate a framework result.

It may provide a partial evaluation where meaningful and clearly label unresolved components.

--------------------------------------------------
FRAMEWORK RESTORATION
--------------------------------------------------

When restoring an old framework:

1. restore the requested version
2. verify provenance
3. verify scope
4. check current applicability
5. check stale/invalid conditions
6. identify material changes in context
7. revalidate before active use

Restoration must not rewrite historical evaluations.

--------------------------------------------------
FRAMEWORK PROVENANCE
--------------------------------------------------

Every framework must preserve:

- creator/source
- original natural-language request
- extracted structure
- evidence requirements
- modification history
- version history
- evaluations using the framework
- relevant research references
- timestamps
- applicable context

The system must be able to explain why a framework has its current structure.

--------------------------------------------------
NATURAL LANGUAGE CONTROL
--------------------------------------------------

Natural language is the primary control surface.

The trader may:

- create frameworks
- rename frameworks
- add/remove factors
- change weights
- change thresholds
- modify conditions
- change evidence requirements
- change evaluation rules
- change scope
- activate/archive
- compare versions
- challenge the framework
- apply a framework
- save a framework
- restore a previous version

The agent maps natural language to structured framework operations.

Internal structure must not require the trader to learn commands.

--------------------------------------------------
CONSEQUENTIAL ACTION BOUNDARY
--------------------------------------------------

Immediate execution is appropriate for:

- evaluating according to an existing framework
- inspecting factors
- analyzing evidence
- temporary evaluation changes
- temporary research scope changes

Confirmation is required for consequential persistent actions such as:

- materially modifying a persistent framework
- replacing an active framework
- deleting a framework permanently
- changing critical rules
- changing hard requirements
- changing persistent weights
- changing persistent thresholds
- activating persistent monitoring

If the trader explicitly requests the persistent change, confirmation may still be required when the consequence is substantial or destructive.

--------------------------------------------------
FRAMEWORK INTEGRITY PRINCIPLE
--------------------------------------------------

The framework must be treated as a methodological contract between the trader and the system.

The system may:

- interpret
- apply
- research missing evidence
- identify weaknesses
- challenge
- explain
- recommend changes
- version
- preserve
- restore
- monitor consequences

The system must not silently:

- change factors
- change weights
- change thresholds
- change hard rules
- change evaluation rules
- remove inconvenient factors
- invent evidence
- convert missing evidence into failure
- convert weak evidence into strong evidence
- rewrite historical evaluations
- rewrite the trader's methodology

--------------------------------------------------

--------------------------------------------------

→ RESOLVE TARGET

→ CHECK APPLICABILITY

→ LOAD FRAMEWORK VERSION

→ INTERPRET FACTORS

→ RESOLVE CONDITIONS

→ IDENTIFY EVIDENCE REQUIREMENTS

→ CHECK AVAILABLE EVIDENCE

→ IDENTIFY MISSING EVIDENCE

→ RESEARCH MISSING INFORMATION WHEN NECESSARY

→ EVALUATE EVIDENCE QUALITY

→ EVALUATE EACH FACTOR

→ APPLY CONDITIONS

→ APPLY THRESHOLDS

→ APPLY EVALUATION RULES

→ RESOLVE FACTOR DEPENDENCIES

→ IDENTIFY CONFLICTS

→ APPLY AGGREGATION MODEL

→ CHECK FRAMEWORK INTEGRITY

→ ASSESS OVERALL RESULT

→ ASSESS CONFIDENCE

→ IDENTIFY UNCERTAINTY

→ IDENTIFY KEY DRIVERS

→ IDENTIFY WHAT COULD CHANGE RESULT

→ PRODUCE CURRENT FRAMEWORK EVALUATION

→ PRESERVE PROVENANCE

→ UPDATE OBJECT GRAPH

→ RECOMMEND RESEARCH / CHALLENGE / MONITOR WHEN WARRANTED

→ COMPLETE

--------------------------------------------------
GLOBAL PRINCIPLE
--------------------------------------------------

A framework tells the system HOW THE TRADER WANTS TO EVALUATE SOMETHING.

The system must faithfully apply that methodology while remaining honest about evidence quality, missing information, uncertainty, and framework limitations.

The system may challenge the framework.

The system may recommend improving the framework.

The system may identify when the framework is inadequate.

But the trader decides whether the framework itself changes.
