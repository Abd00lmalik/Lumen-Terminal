# Research Object Model

## 1. Object hierarchy

The model should look like this:

```text
WORKSPACE
│
├── RESEARCH
│   ├── BRANCH
│   ├── CLAIM
│   ├── EVIDENCE
│   ├── HYPOTHESIS
│   ├── JUDGMENT
│   └── ANALYSIS
│
├── THESIS
├── FRAMEWORK
├── MONITOR
├── SOURCE
├── SNAPSHOT
├── ANNOTATION
└── SAVED ARTIFACT
```

But these aren't all equal.

There are four conceptual layers:

```text
CONTEXT OBJECTS
    Thesis
    Framework
    Preference

RESEARCH OBJECTS
    Research
    Branch
    Claim
    Evidence
    Hypothesis
    Analysis
    Judgment

CONTINUITY OBJECTS
    Monitor
    Snapshot
    Annotation

PROVENANCE OBJECTS
    Source
    Artifact
    Version
```

This distinction matters because a `SOURCE` isn't equivalent to a `THESIS`.

---

# 2. RESEARCH

`RESEARCH` is the primary investigation object.

It represents a trader's attempt to answer a particular question or achieve a particular research objective.

It owns the active investigation context.

```text
RESEARCH {
  id
  objective
  question
  intent
  flow
  target
  scope
  depth
  constraints
  context

  status
  priority

  branches[]
  claims[]
  evidence[]
  hypotheses[]
  analyses[]
  judgments[]

  active_branch
  current_judgment

  created_at
  updated_at

  provenance
  history
}
```

Possible lifecycle:

```text
DRAFT
ACTIVE
PAUSED
COMPLETED
SUPERSEDED
ARCHIVED
```

A research object can be restored.

A completed research object is not destroyed when a new research question replaces it.

---

# 3. BRANCH

A `BRANCH` represents an independent line of investigation inside research.

For example:

```text
Research:
Why did BTC fall?

Branches:
├── Macro explanation
├── Liquidation explanation
├── ETF-flow explanation
└── Regulatory-news explanation
```

A branch has:

```text
BRANCH {
  id
  research_ref
  parent_branch_ref
  objective
  hypothesis_refs[]
  evidence_refs[]
  claim_refs[]
  status
  priority
  depth
  dependencies[]
  created_from
  provenance
}
```

Branches can:

* run independently;
* be paused;
* resume;
* be reprioritized;
* be cloned;
* become obsolete;
* be archived.

Your previous decision that the agent should preserve unrelated work means branch interruption must never unnecessarily destroy other branches.

---

# 4. CLAIM

A `CLAIM` is a proposition that the research is attempting to establish, weaken, or evaluate.

Example:

> “The BTC decline was primarily driven by liquidation.”

The claim isn't necessarily true.

It is something that requires evidence.

```text
CLAIM {
  id
  statement
  type
  status
  importance

  evidence_refs[]
  hypothesis_refs[]

  support_strength
  contradiction_refs[]

  provenance
  created_at
  updated_at
}
```

Possible status:

```text
UNTESTED
SUPPORTED
WEAKLY_SUPPORTED
CONTESTED
WEAKENED
REJECTED
INCONCLUSIVE
```

This gives us an important separation:

**Evidence does not directly become judgment.**

Evidence supports or contradicts claims.

---

# 5. EVIDENCE

`EVIDENCE` is an observed or retrieved piece of information that bears on a claim or hypothesis.

Examples:

* exchange liquidation data;
* CPI release;
* ETF flow data;
* a verified announcement;
* historical price data;
* on-chain activity.

```text
EVIDENCE {
  id

  observation
  evidence_type

  source_refs[]
  timestamp
  observed_at

  supports[]
  contradicts[]

  directness
  reliability
  recency
  specificity
  corroboration

  interpretation
  status

  provenance
}
```

Important distinction:

```text
SOURCE
   ↓
EVIDENCE
   ↓
CLAIM
   ↓
HYPOTHESIS
   ↓
JUDGMENT
```

A source is not automatically evidence.

A source may contain multiple pieces of evidence.

---

# 6. SOURCE

`SOURCE` represents the origin from which information was obtained.

Examples:

```text
Bitget market data
Reuters article
Federal Reserve publication
Glassnode dataset
on-chain RPC data
official project announcement
```

```text
SOURCE {
  id
  type
  locator
  publisher
  author
  published_at
  retrieved_at

  reliability
  provenance

  content_reference
}
```

The source object allows the system to answer:

> “Where did this claim come from?”

This is essential to your evidence-chain requirement.

---

# 7. HYPOTHESIS

A `HYPOTHESIS` is a candidate explanation or interpretation being investigated.

Example:

> “BTC dropped because leveraged positions were liquidated after the macro announcement.”

```text
HYPOTHESIS {
  id
  statement
  type

  supporting_claims[]
  contradicting_claims[]

  evidence_refs[]
  dependencies[]

  alternatives[]
  ranking
  confidence

  status

  created_at
  updated_at
  provenance
}
```

Possible status:

```text
CANDIDATE
UNDER_INVESTIGATION
LEADING
WEAKENED
SUPPORTED
REJECTED
INCONCLUSIVE
HISTORICAL
```

Hypotheses are living objects.

They change as evidence changes.

---

# 8. ANALYSIS

`ANALYSIS` represents a deliberate analytical operation performed on evidence, claims, hypotheses, or other research objects.

This is useful because `ANALYZE` is an action, while the resulting analysis can become an object.

Example:

```text
ANALYSIS
"Compare the macro explanation against the liquidation explanation."
```

```text
ANALYSIS {
  id
  objective
  mode
  target_refs[]

  inputs[]
  findings[]
  relationships[]

  supporting_evidence[]
  opposing_evidence[]

  conclusion
  uncertainty
  confidence

  provenance
  created_at
  updated_at
}
```

Modes:

```text
COMPARE
EXPLAIN
INTERPRET
SYNTHESIZE
```

---

# 9. JUDGMENT

A `JUDGMENT` is the current best-supported assessment produced by research or analysis.

This is one of the most important objects.

It should not simply be a text response.

```text
JUDGMENT {
  id
  statement

  basis {
    supporting_evidence[]
    opposing_evidence[]
    key_claims[]
    hypotheses[]
  }

  confidence
  uncertainty

  implications[]
  unresolved_questions[]

  status

  created_at
  updated_at

  provenance
  previous_judgment_ref
}
```

A research investigation can have multiple historical judgments but only one **current judgment**.

Example:

```text
Judgment v1:
"Macro news was probably the primary driver."

New evidence arrives.

Judgment v2:
"Liquidations appear to have been the primary driver, while macro news was an initiating catalyst."
```

v1 remains in history.

v2 becomes current.

This directly follows your repeated requirement that **new evidence changes the current state without destroying historical state**.

---

# 10. THESIS

A `THESIS` is a trader-level belief or proposition that exists beyond one research investigation.

This distinction is important.

A judgment answers:

> “What does the current evidence suggest?”

A thesis says:

> “What do I believe about the market?”

Example:

```text
JUDGMENT
"Current evidence supports continued weakness."

THESIS
"BTC will remain below $X unless liquidity conditions improve."
```

```text
THESIS {
  id
  statement

  claims[]
  assumptions[]
  dependencies[]
  expected_outcome[]

  supporting_research[]
  supporting_evidence[]

  invalidation_conditions[]

  confidence
  status

  created_at
  updated_at

  provenance
  history
}
```

This is why `CHALLENGE` needs its own target model.

It can challenge a thesis that exists independently of the current research.

---

# 11. FRAMEWORK

A `FRAMEWORK` is a persistent evaluation methodology belonging to the trader.

You already defined its internal structure:

```text
FRAMEWORK {
  id
  name

  factors[] {
    factor
    condition
    evidence_required
    weight
    threshold
    evaluation_rule
  }

  version
  status

  provenance
  history
}
```

A framework can be reused across many research investigations.

For example:

```text
Research A
   ↓
Evaluate using BTC Swing Framework

Research B
   ↓
Evaluate using BTC Swing Framework
```

The framework itself remains independent.

---

# 12. MONITOR

`MONITOR` is a persistent continuity object.

It references existing research rather than becoming detached from it.

```text
MONITOR {
  id

  objective
  original_research_ref

  thesis_refs[]
  judgment_refs[]
  hypothesis_refs[]
  condition_refs[]

  signals[]
  trigger_rules[]

  status
  severity
  frequency

  reassessment_policy

  alert_history
  adaptation_history

  provenance
  lineage
}
```

This allows:

```text
RESEARCH
   ↓
JUDGMENT
   ↓
THESIS
   ↓
MONITOR
   ↓
NEW EVIDENCE
   ↓
REASSESSMENT
```

Exactly the persistent loop we designed.

---

# 13. SNAPSHOT

A `SNAPSHOT` captures workspace state at a particular point in time.

It is not merely a copy of the UI.

It captures the logical research state.

```text
SNAPSHOT {
  id
  workspace_ref

  research_refs[]
  branch_refs[]
  evidence_refs[]
  hypothesis_refs[]
  judgment_refs[]
  thesis_refs[]
  framework_refs[]
  monitor_refs[]

  relationships
  dependencies

  timestamp
  provenance
}
```

This enables:

> “Restore my research to where it was before we changed the scope.”

---

# 14. ANNOTATION

`ANNOTATION` allows the trader or agent to attach contextual information without changing the underlying research object.

Examples:

> “Trader considers this source highly reliable.”

> “This hypothesis was suggested after the FOMC announcement.”

```text
ANNOTATION {
  id
  target_ref
  author
  content
  type
  timestamp
  provenance
}
```

Annotations should not silently become evidence.

---

# 15. SAVED ARTIFACT

`SAVE` does not need a completely separate underlying research object type.

Instead, it creates a persistent artifact/reference around an existing object.

For example:

```text
SAVE
  ↓
Research #123
  ↓
Saved Artifact
  ↓
"My BTC Macro Research — September 2026"
```

The artifact preserves:

* object reference;
* version;
* provenance;
* timestamp;
* destination;
* status.

This keeps `SAVE` as an action rather than duplicating the object model.

---

# 16. Relationships

This is a major part of the architecture.

Objects should be connected through explicit relationships.

```text
SOURCE
   ↓ supports
EVIDENCE
   ↓ supports
CLAIM
   ↓ contributes_to
HYPOTHESIS
   ↓ informs
JUDGMENT
   ↓ informs
THESIS
   ↓ monitored_by
MONITOR
```

But relationships can also be:

```text
supports
contradicts
derived_from
depends_on
tests
challenges
references
supersedes
replaces
related_to
caused_by
part_of
branched_from
```

This is what gives the workbench its actual research graph.

---

# 17. Object Ownership

The ownership model should be hybrid.

```text
RESEARCH
owns active investigation state

BRANCH
belongs to research

CLAIM
usually belongs to research but can persist through references

EVIDENCE
can be reused across research

HYPOTHESIS
belongs to research but may become historical/persistent

JUDGMENT
belongs to a research context and has historical versions

THESIS
persists independently

FRAMEWORK
persists independently

MONITOR
persists independently

SOURCE
persists independently

SNAPSHOT
belongs to workspace state
```

This prevents duplicated evidence and duplicated knowledge.

---

# 18. Object Lifecycle

Every significant object should have lifecycle state.

General model:

```text
CREATED
   ↓
ACTIVE
   ↓
UPDATED
   ↓
COMPLETED / PAUSED / SUPERSEDED
   ↓
ARCHIVED
```

Deletion is separate.

```text
ARCHIVED
   ↓
RESTORED
```

Permanent deletion requires explicit confirmation.

---

# 19. Object Versioning

Material changes create versions.

```text
Judgment v1
    ↓
material evidence
    ↓
Judgment v2
```

The system retains:

```text
CURRENT
HISTORICAL
```

rather than overwriting the past.

Minor internal changes don't need to generate noisy versions.

---

# 20. Freshness

Every evidence-bearing object should have freshness metadata where relevant.

For example:

```text
EVIDENCE
freshness = CURRENT

OLD RESEARCH
freshness = STALE

HISTORICAL EVENT
freshness = HISTORICAL
```

Crucially:

> **Stale does not mean deleted.**

It means the information should not automatically be treated as current evidence.

This directly matches your previous decisions around restoring old research.

---

# 21. Provenance

Every meaningful object should be traceable.

The system should be able to traverse:

```text
Judgment
↓
Hypothesis
↓
Claim
↓
Evidence
↓
Source
```

and also:

```text
Thesis
↓
Research
↓
Judgment
↓
Evidence
```

So if the trader asks:

> “Why do you believe this?”

the system doesn't need to reconstruct its reasoning from scratch.

It follows the object graph.

# 23. The Most Important Distinctions

There are four distinctions I would treat as architectural rules.

### Evidence ≠ Claim

Evidence is what was observed.

A claim is what the evidence may support.

### Claim ≠ Hypothesis

A claim is a proposition.

A hypothesis is a candidate explanatory model connecting claims and evidence.

### Judgment ≠ Thesis

A judgment is the system's current evidence-based assessment.

A thesis is the trader's persistent belief or market proposition.

### Research ≠ Conversation

A conversation is the interaction.

A research object is the persistent intellectual work produced through that interaction.

This distinction is extremely important for the product.

# 24. What This Means for the Agent

Now your original `AGENT.md` idea becomes much more powerful.

The agent can reason in terms of actual objects:

```text
User asks question
       ↓
Create / identify RESEARCH
       ↓
Create BRANCHES
       ↓
Collect SOURCES
       ↓
Create EVIDENCE
       ↓
Create / update CLAIMS
       ↓
Create / update HYPOTHESES
       ↓
Perform ANALYSIS
       ↓
Produce JUDGMENT
       ↓
Relate to THESIS if relevant
       ↓
Offer MONITORING
       ↓
SAVE if requested
```

The agent isn't simply following a huge prompt.

It is operating on a **structured research environment**.

That is the direction I would lock.
