RESEARCH STATE / WORKSPACE PRESENTATION INTELLIGENCE

## 1. Purpose

Research State / Workspace Presentation Intelligence defines how the internal research graph becomes a usable trader-facing workspace.

It controls:

- what is visible
- what is prioritized
- what is collapsed
- what is interactive
- what changes in real time
- how research progress is represented
- how evidence and reasoning are exposed
- how multiple branches are presented
- how the trader moves from overview to detail

It does not determine the underlying research truth.

Its responsibility is:

```text
INTERNAL RESEARCH STATE
```text
        ↓
PRESENTATION STATE
        ↓
TRADER INTERFACE
        ↓
TRADER ACTION
        ↓
UPDATED RESEARCH STATE
        ↓
```
UPDATED PRESENTATION
```

The workspace is not a static report.

It is a living representation of the current research state.

---

# 2. Core Principle

The workspace should expose the most decision-relevant information first while preserving access to the complete research trail.

The presentation hierarchy is:

```text
CURRENT JUDGMENT
```text
        ↓
WHY
        ↓
WHAT SUPPORTS IT
        ↓
WHAT WEAKENS IT
        ↓
WHAT REMAINS UNCERTAIN
        ↓
ACTIVE HYPOTHESES / BRANCHES
        ↓
DETAILED EVIDENCE
        ↓
```
FULL TRACEABILITY
```

The trader should not need to read the entire research process to understand the current conclusion.

---

# 3. Presentation vs Research State

Research state is authoritative.

Presentation state is a view of research state.

Therefore:

```text
Presentation changes
≠
Research changes
```

For example:

```text
"Collapse the evidence section."
```

changes presentation state only.

While:

```text
"Remove that evidence."
```

is a research/state operation.

The distinction must always be preserved.

# 6. Research Header

Every active research workspace should expose a compact header containing:

* research question
* target
* timeframe
* research flow
* current status
* current depth
* freshness
* active constraints
* last meaningful update

Example:

```text
BTC fell 8% over the last 24 hours

Flow:
Why did it happen?

Status:
Active

Depth:
Deep

Updated:
2 minutes ago
```

The header provides orientation without requiring the trader to inspect the research graph.

---

# 7. Current Judgment

The current judgment is the most important presentation object.

It should normally appear near the top.

Default presentation:

```text
CURRENT JUDGMENT

BTC's decline appears primarily associated with
a combination of liquidation pressure and worsening
risk sentiment.

Confidence: Moderate

Main support:
• ...
• ...

Main weakness:
• ...

What could change this:
• ...
```

The exact prose is generated by Judgment & Confidence Intelligence.

Presentation Intelligence determines how it is displayed.

---

# 8. Judgment Status

The workspace should visually distinguish:

```text
CONFIDENT
MODERATE
LOW
INSUFFICIENT EVIDENCE
CONTESTED
UNRESOLVED
```

No numerical confidence percentage should be fabricated.

Qualitative confidence is the default.

---

# 9. Judgment History

The current judgment is primary.

Previous material judgments remain accessible.

Example:

```text
Current:
Liquidation pressure is the strongest explanation.

Previous:
Macro uncertainty was initially considered dominant.

Change:
New derivatives evidence shifted the assessment.
```

This allows the trader to understand how the conclusion evolved.

---

# 10. Why Panel

The workspace should provide a direct path from judgment to explanation.

Default:

```text
WHY THIS JUDGMENT?

1. Strongest supporting evidence
2. Key causal relationship
3. Leading hypothesis
4. Main opposing evidence
5. Remaining uncertainty
```

The trader should be able to expand each component.

---

# 11. Evidence Presentation

Evidence should not appear as an undifferentiated feed.

Each evidence item should expose, at minimum:

```text
OBSERVATION
SOURCE
TIME
RELATION TO CLAIM
EVIDENCE TYPE
RELIABILITY / RELEVANCE
```

Example:

```text
Funding turned sharply negative
Source: derivatives data
Observed: 09:42 UTC
Supports: liquidation-pressure hypothesis
Type: quantitative observation
```

---

# 12. Evidence Classification

The interface should distinguish:

```text
FACTUAL OBSERVATION
QUANTITATIVE OBSERVATION
MARKET DATA
ON-CHAIN OBSERVATION
DOCUMENTED STATEMENT
HISTORICAL RECORD
EXPERT INTERPRETATION
ANALYST INTERPRETATION
SENTIMENT SIGNAL
INFERENCE
SPECULATION
```

The presentation must not make speculative information visually equivalent to direct observations.

---

# 13. Source Presentation

Sources should be accessible directly from evidence.

Source presentation should include:

* publisher
* source type
* publication time
* retrieval time
* source status
* relevant excerpt/reference when available
* relationship to the evidence

The interface should not imply that multiple articles are independent evidence when they originate from the same underlying source.

---

# 14. Evidence Relationships

The trader should be able to see how evidence relates to the research.

Example:

```text
Evidence
   ↓ supports
Claim
   ↓ supports
Hypothesis
   ↓ contributes to
Judgment
```

Contradictory evidence should be equally accessible.

The interface should not hide evidence simply because it weakens the current conclusion.

---

# 15. Supporting vs Opposing Evidence

The workspace should maintain two distinct presentation groups:

```text
SUPPORTING
OPPOSING
```

Additional categories may include:

```text
QUALIFYING
CONTEXTUAL
NEUTRAL
DOES NOT ADDRESS
```

This prevents the interface from becoming confirmation-biased.

---

# 16. Hypothesis Presentation

Active hypotheses should appear as competing explanations rather than a flat list.

Example:

```text
HYPOTHESES

1. Liquidation cascade
   Leading
   Moderate confidence

2. Macro risk-off
   Supported
   Moderate confidence

3. Exchange-specific event
   Weakened
   Low confidence
```

The interface should make ranking visible without presenting ranking as certainty.

---

# 17. Hypothesis Comparison

Selecting a hypothesis should expose:

* supporting evidence
* contradicting evidence
* assumptions
* expected observations
* disconfirming observations
* alternatives
* confidence
* ranking
* unresolved questions

This provides progressive disclosure.

Example:

ACTIVE RESEARCH

├── Macro explanation
│   ├── Evidence

```

Branch status should be visible:

```text
ACTIVE
PAUSED
COMPLETED
BLOCKED
FAILED

```

# 19. Branch Priority

When multiple branches exist, the interface should expose relative priority where useful.

Possible presentation:

```text
High priority
Medium priority
Low priority
```

The exact scheduler score should remain hidden by default.

Detailed scheduling information can be exposed on demand.

# 20. Active Research Progress

Progress should represent meaningful research progress rather than arbitrary task percentages.

Useful states:

```text
INTERPRETING
PLANNING
DISCOVERING
INVESTIGATING
VALIDATING
TESTING HYPOTHESES
SYNTHESIZING
ASSESSING CONFIDENCE
COMPLETE
```

The interface may show:

```text
Researching 3 hypotheses
Validating 12 evidence items
2 branches active
1 contradiction under investigation
```

This is more useful than:

```text
67% complete
```

# 21. Research Activity

The workspace should expose meaningful live activity.

Example:

```text
Research activity

✓ Macro data checked
✓ Derivatives evidence collected
→ Investigating liquidation hypothesis
→ Cross-checking exchange reports
○ Historical comparison pending
```

Activity should communicate what the system is doing without exposing unnecessary internal reasoning.

# 22. Internal Reasoning Boundary

The workspace should not expose hidden chain-of-thought.

Instead it should expose:

* evidence
* claims
* hypotheses
* relationships
* analytical findings
* conclusions
* confidence
* decision-relevant rationale

The trader receives traceability without private internal reasoning.

# 31. Timeline Presentation

The workspace should maintain a research timeline containing material events.

Example:

```text
10:02; Research started
10:05; Initial hypothesis created
10:11; Macro evidence collected
10:17; Contradictory evidence discovered
10:21; Liquidation hypothesis promoted
10:28; Judgment revised
```

Minor internal operations should not flood the timeline.

---

# 32. Materiality Filter

Presentation should prioritize material events.

Material events include:

* judgment changes
* hypothesis ranking changes
* important contradictions
* thesis changes
* major scope changes
* meaningful confidence changes
* new invalidation conditions
* significant source corrections
* major monitor adaptations

Routine internal operations remain available through deeper history.

---

# 33. Contradiction Presentation

Contradictions should be visible rather than buried.

Example:

```text
CONFLICT

Current hypothesis:
Liquidation pressure

Contradicting evidence:
Price decline began before major liquidation spike.

Status:
Under investigation

Impact:
Moderately weakens causal confidence
```

The system should communicate the effect of contradiction, not merely its existence.

---

# 34. Uncertainty Presentation

Uncertainty should be presented as a first-class state.

Example:

```text
UNCERTAINTY

Main unresolved issue:
Whether the macro announcement preceded
the observed market shift.

Impact:
Material

Research status:
Investigating
```

This is more useful than simply displaying “Confidence: Moderate.”

---

# 35. Freshness Presentation

Where freshness materially affects the conclusion, the workspace should show it.

Possible states:

```text
CURRENT
RECENT
AGING
STALE
INVALID
UNKNOWN
```

Historical information should be visibly distinguished from current evidence.

---

# 36. Scope Presentation

# 37. Depth Presentation

Current research depth should be visible without exposing internal scheduler complexity.

Example:

```text
Depth:
Deep
```

The trader may change it naturally:

```text

# 38. Filters

The workspace may provide filters such as:

```text

# 39. Presentation Filter Boundary

Important distinction:

```text
"Show only macro evidence."
```

= presentation filter.

```text
"Research only macro evidence."
```

= research scope change.

The system must not confuse the two.

---

# 40. Pinning

The trader may pin:

* judgments
* hypotheses
* evidence
* claims
* thesis
* framework
* monitor
* annotations

Pinning changes presentation priority only.

---

# 41. Hiding

Objects may be hidden from the primary workspace without deletion.

Hidden objects remain available through the research graph.

Example:

```text
"Hide the sentiment branch."
```

does not stop the branch.

Stopping requires an explicit state operation.

---

# 42. Collapse / Expand

Sections can be collapsed or expanded.

Examples:

```text
Collapse evidence.
Expand the leading hypothesis.
Show the full source trail.
```

These are presentation commands.

---

# 43. Selection State

The workspace should maintain one primary selected object where appropriate.

Selection should not change research state.

It simply determines what the detail panel displays.

---

# 44. Relationship View

The trader should be able to inspect relationships between objects.

Example:

```text
Evidence
   ↓ supports
Claim
   ↓ supports
Hypothesis
   ↓ contributes to
Analysis
   ↓ informs
Judgment
   ↓ evaluates
Thesis
```

The graph should be selectively expanded rather than displaying the entire graph by default.

---

# 45. Dependency Indicators

Objects affected by another object's material change should be identifiable.

Example:

```text
Evidence updated

Affected:
→ Claim A
→ Hypothesis B
→ Current Judgment
→ Active Monitor
```

This makes propagation understandable.

---

# 46. State Change Presentation

When a material state changes, the workspace should communicate:

```text
WHAT CHANGED
WHY IT CHANGED
WHAT IT AFFECTED
WHAT THE CURRENT STATE IS
```

Example:

```text
Judgment updated

Reason:
New derivatives evidence materially weakened
the previous explanation.

Affected:
Current hypothesis ranking
Confidence
Monitor assessment
```

---

# 47. Automatic Updates

The workspace should update automatically when research state changes.

However, updates should be grouped to prevent visual noise.

Multiple related changes may appear as one meaningful event.

---

# 48. Trader Intervention

The trader can interact with presentation state through natural language.

Examples:

```text

"Hide the historical branch."

"Pin the current judgment."

"Open the evidence behind this claim."

"Compare these two hypotheses."

"Show everything that changed since yesterday."
```

These requests should map to presentation or analytical actions depending on intent.

# 60. Responsive Presentation

The information hierarchy must survive different screen sizes.

On constrained screens:

```text
Judgment
→ Key evidence
→ Main uncertainty
→ Hypotheses
→ Everything else
```

The interface should not simply shrink every component.

It should prioritize information.

# 61. Live Research State

While research is running, the workspace should remain interactive.

The trader should be able to say:

```text
"Stop looking at sentiment."

"Go deeper on the second hypothesis."

"Add macro."

"Challenge the current explanation."

"Ignore that source."

"Focus only on the last week."
```

The workspace should immediately reflect the resulting state transition.

---

# 62. Concurrent Research Presentation

If several branches execute simultaneously, the workspace should show them as concurrent investigations.

Example:

```text
Researching

Branch A; Macro
████████░░

Branch B; Derivatives
██████░░░░

Branch C; News
██████████
```

Progress bars are optional presentation aids.

The underlying scheduler remains authoritative.

---

# 63. Waiting / Blocked States

The interface should distinguish:

```text
WAITING
BLOCKED
FAILED
PAUSED
```

They should not all appear as simply “not running.”

Where useful, the reason should be shown.

---

# 64. Failure Presentation

If a tool or source fails:

Low

Used

```

# 65. Incomplete Research

Incomplete research should be explicitly labeled.

Example:

```text

Incomplete

Historical data source unavailable

Provisional
```

# 66. Completion Presentation

When research completes, the workspace should transition from execution-focused presentation to judgment-focused presentation.

Default final structure:

```text
FINAL JUDGMENT
WHY
STRONGEST EVIDENCE
OPPOSING EVIDENCE
KEY UNCERTAINTIES
WHAT WOULD CHANGE THE ASSESSMENT
CONFIDENCE
```

Relevant branches and evidence remain accessible.

---

# 67. Stale Research Presentation

If research becomes stale:

```text
Research:
STALE

Reason:
Current market conditions have changed.

Historical conclusion:
Preserved

Current use:
Historical context only
```

Restoration requires revalidation.

---

# 68. Archived Research Presentation

Archived research should be accessible but visually separated from active research.

Restoring it should trigger:

```text
RESTORE
→ REHYDRATE
→ CHECK FRESHNESS
→ REVALIDATE
→ REACTIVATE IF VALID
```

---

# 69. Saved Artifacts

Saved artifacts should be accessible without duplicating the underlying research.

Example:

---

# 70. Presentation Versioning

Presentation changes do not create research versions.

Research object versions are created only when the underlying state changes materially according to the relevant intelligence layer.

---

# 71. Personalization

Presentation may adapt to durable trader preferences:

* preferred depth
* preferred domains
* preferred evidence visibility
* preferred notification density
* preferred workspace mode

Personalization should not override current explicit requests.

---

# 72. No Silent Information Loss

Collapsing, filtering, hiding, or switching modes must never delete or invalidate research information.

The complete research graph remains recoverable.

---

# 73. No Confirmation Bias Through Presentation

The interface must not selectively foreground supporting evidence while burying opposing evidence.

Default judgment presentation should include both:

```text
WHY IT MAY BE RIGHT
+
WHY IT MAY BE WRONG
```

when meaningful opposing evidence exists.

---

# 74. Presentation Materiality

Not every internal state update needs to be presented.

The system should surface changes when they materially affect:

* judgment
* confidence
* thesis
* hypothesis ranking
* research scope
* monitoring
* evidence validity
* decision relevance

Minor internal changes may remain in detailed history.

---

# 75. Presentation Provenance

Every displayed conclusion, evidence item, hypothesis, and material state change should be traceable to its underlying object.

The presentation layer should never create an untraceable claim.

---

# 76. Presentation Integrity

The workspace must preserve:

```text
OBJECT IDENTITY
OBJECT STATE
OBJECT RELATIONSHIPS
PROVENANCE
VERSION
TIMESTAMP
CONTEXT
```

Presentation transformations must not corrupt research semantics.

---

# 77. Interaction With Context Intelligence

Context Intelligence determines what the trader means.

Presentation Intelligence determines how the resolved state is shown.

Example:

```text
"Show me why the other explanation is weaker."

Context:
Other explanation = Hypothesis B

Action:
ANALYZE / PRESENT

Presentation:
Hypothesis B detail + opposing evidence
```

# 78. Interaction With LUI

Natural language can control presentation directly.

Examples:

```text
"Show the strongest evidence."

"Expand the macro branch."

"Hide the old hypothesis."

"Pin this judgment."

"Give me the full evidence trail."

"Switch to timeline view."
```

The LUI layer maps these requests to presentation operations.

---

# 79. Interaction With MANAGE_STATE

If a request changes actual research state rather than presentation state, it must route to MANAGE_STATE.

Example:

```text
"Hide the branch."
→ presentation operation

"Pause the branch."
→ MANAGE_STATE
```

---

# 80. Interaction With Analysis

When the trader asks:

```text
"Compare these two hypotheses."
```

the system should invoke ANALYZE and then present the resulting comparison.

Presentation Intelligence does not perform the comparison itself.

---

# 81. Interaction With Challenge

When the trader says:

```text
"Challenge this."
```

CHALLENGE performs the stress test.

Presentation Intelligence displays:

```text
Verdict
Weak points
Counter-evidence
Alternative explanations
Invalidation conditions
```

---

# 82. Interaction With Monitor

When a monitor generates a material update, the workspace should surface:

```text
WHAT CHANGED
WHY IT MATTERS
CURRENT ASSESSMENT
CONFIDENCE
ACTION RECOMMENDATION IF ANY
```

The trader remains the decision-maker.

---

# 83. Interaction With Save

SAVE may preserve:

* research result
* framework
* thesis
* snapshot
* workspace state
* reusable artifact

The presentation layer should make the saved object's origin and version clear.

---

# 84. Interaction With Memory

Memory-derived information should be visually or semantically distinguishable when it materially affects the result.

Example:

```text
Historical context:
A similar event occurred in 2024.

Current evidence:
...
```

The interface must not blend these into one evidence pool.

```text

Presentation Intelligence is complete when:

* current judgment is clearly visible
* research status is understandable
* major evidence is accessible
* opposing evidence is visible
* hypotheses are distinguishable
* branches are understandable
* uncertainty is visible
* thesis/framework context is distinguishable
* provenance is accessible
* material state changes are visible
* historical state is distinguishable from current state
* presentation actions cannot silently mutate research
* the trader can navigate from summary to full traceability
* natural-language presentation commands are supported
